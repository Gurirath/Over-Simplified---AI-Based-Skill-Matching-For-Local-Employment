# REACH — Handoff for UI builders

This assumes you haven't seen this code before. REACH is a local job-matching system: a
candidate's spoken story goes in, a structured skill profile with traceable evidence comes out,
jobs get filtered by whether the candidate can *actually take* them (not just "is a good fit"),
and an optimizer computes the minimum skill(s) to learn to unlock the most jobs. Full product
rationale is in `CLAUDE.md` — read that if you want the "why," this doc is the "how do I call it."

**You do not need a Gemini API key to build the UI.** Every LLM response for the 4 demo personas
is already committed to `data/cache/` (hashed filenames, keyed by exact prompt text — see
"The cache" below). `lib/llmCache.ts` checks that cache before ever touching the network. If you
only ever submit the 4 personas' exact `rawStory` text through `/api/extract-candidate`, you will
get a cache hit every time and the app runs with zero network calls. The Beat-7 vacancy text from
`DEMO.md` also has a cache entry, but as of this doc it's still sitting uncommitted alongside
`DEMO.md` and this file — pull latest before relying on it, or ask whoever wrote `DEMO.md` to
confirm it landed. Only a genuinely new story/vacancy triggers a real API call — that path is
exercised by the API routes at `app/api/extract-candidate/route.ts` and
`app/api/extract-job/route.ts`, not anything you need to build.

There is **no database**. Everything is JSON files under `data/`, imported at build time.

## 1. Data files

### `data/skills.json` → `Skill[]`

The controlled vocabulary, ~113 entries. Generated by `scripts/gen_skills.py` — don't hand-edit
the JSON, edit the generator and re-run it.

```ts
interface Skill {
  id: string;              // "SKILL_TALLY_BASIC" — stable, used everywhere else as a foreign key
  canonicalName: string;   // "Tally (Basic)" — what you show in the UI
  aliases: string[];       // surface forms incl. Hinglish, lowercased — not usually needed in UI
  category: SkillCategory; // one of 9 categories, e.g. "retail_sales", "trades"
  prerequisites: string[]; // other skill IDs, usually []
  learnHours: number;      // hours to competence — this is what "jobs per 10 hours" divides by
  learnCostBand: "free" | "low" | "medium" | "high";
  verifiableBy: string;    // human-readable, e.g. "Stock reconciliation exercise" — display only
}
```

### `data/jobs.json` → `Job[]`

250 synthetic listings for Vellore/Katpadi. **The UI must show a visible chip labelling this
corpus as synthetic, with its size and area — never hide it** (CLAUDE.md §6).

```ts
interface Job {
  id: string;
  title: string;
  employerName: string;
  employerType: EmployerType;   // "kirana" | "bakery" | ... | "other"
  location: { lat: number; lng: number };
  areaName: string;             // "Katpadi" — for display
  requiredSkills: string[];     // skill IDs — MUST all be held or the job is unqualified
  preferredSkills: string[];    // skill IDs — improves score, never gates feasibility
  salaryMin: number;
  salaryMax: number;
  shift: { startMin: number; endMin: number; days: number[] }; // minutes from midnight, 0=Sun
  hoursPerWeek: number;
  hardEligibility: string[];    // e.g. ["two_wheeler_licence"] — usually []
  minExperienceMonths: number;
  rawDescription?: string;      // only present if created via employer intake, not the corpus
  isSynthetic: boolean;         // true for all 250 corpus jobs, false for live-created ones
}
```

### `data/personas.json` → 4 demo personas

No login/accounts in this app — the persona switcher (a dropdown, not auth) is how a judge picks
who's "logged in." Each entry:

```ts
interface Persona {
  id: string;              // fixed IDs: PERSONA_DEVI, PERSONA_KAVITHA, PERSONA_RAMESH, PERSONA_PRIYA
  displayName: string;
  age: number;
  note: string;             // internal only — validated numbers, do not render in the UI
  location: { lat: number; lng: number };
  areaName: string;
  rawStory: string;         // feed this verbatim into POST /api/extract-candidate
  expectedSkillIds: string[]; // EVAL GROUND TRUTH ONLY — not what the app should show as her
                              // skills. Her real skills come from actually calling the extraction
                              // route (or reading the cache) and running ingestCandidateExtraction.
  constraints: CandidateConstraints; // matches lib/types.ts exactly — feed straight into Candidate
}
```

`PERSONA_DEVI` is the primary demo persona (`note` says so) — she's the only one where confirming
an implied claim changes her qualified count, which is the entire point of the verification screen.
See `DEMO.md` for her numbers.

**Do not build a candidate object from `expectedSkillIds`.** That field is eval ground truth
(hand-labelled for `scripts/eval.ts`), not the candidate's actual skill claims. A past bug in
`scripts/check-personas.ts` did exactly this and produced wrong qualified counts — see its
current version for the correct pattern (cache → `ingestCandidateExtraction` → `heldSkillIds`).

### `data/eval-stories.json`

9 additional hand-labelled stories for the eval harness (`scripts/eval.ts`). Not used by the app
at runtime — ignore this file unless you're touching the eval.

### `data/cache/*.json` — one file per cached LLM call

Filename is a sha256 hash (see "The cache" below). Contents:

```ts
interface CacheEntry {
  raw: string;              // the raw JSON text the model returned, NOT yet parsed/validated
  model: string;             // "gemini-3.5-flash"
  kind: "candidate-extraction" | "job-extraction";
  personaId?: string;        // present for persona cache entries, informational only
}
```

You will not read these files directly — `lib/llmCache.ts` and the two API routes handle it.

## 2. The two API routes

Both are Next.js route handlers. Both are cache-first (see §3 below) and both validate the
model's JSON before trusting it, retrying once on malformed output before falling back to
whatever's cached.

### `POST /api/extract-candidate`

```
Request:  { "story": string }
Response: CandidateIngestResult & { fromCache: boolean }

CandidateIngestResult = {
  claims: SkillClaim[];          // her skill profile — this is what you render
  unmatchedMentions: string[];   // model proposed a skill, normalizer couldn't map it — debug info
  droppedForBadSpan: string[];   // model's evidence span wasn't verbatim in the story — dropped
}
```

Errors: `400` if `story` is missing/empty. `502` if the Gemini call itself failed (network/auth/
rate-limit) or if both attempts produced malformed JSON with nothing cached to fall back to —
body is `{ error: string, detail?: string }`.

### `POST /api/extract-job`

```
Request: {
  "description": string,
  "id": string,
  "employerName": string,
  "location": { "lat": number, "lng": number },
  "areaName": string
}
Response: JobIngestResult & { fromCache: boolean }

JobIngestResult = {
  job: Job;                  // ready to push into your jobs list / feed straight into feasibility
  unmatchedMentions: string[];
  missingFields: string[];   // employer didn't say salary/shift/hours — UI should prompt for these
}
```

Errors: `400` if any required field is missing. `502` same as above.

Both routes read `GEMINI_API_KEY` from the server environment — never call Gemini directly from
client code, that's why these are API routes and not client-side fetches to Google.

## 3. The cache, explained

`lib/llmCache.ts` — three functions, no LLM calls in this file:

```ts
cacheKey(kind: string, systemPrompt: string, userPrompt: string): string
// sha256 of "kind system-prompt user-prompt". Same story text -> same key, every time.

readCachedResponse(key: string): string | null
// reads data/cache/{key}.json, returns the raw model text, or null on a miss.

writeCachedResponse(key: string, raw: string, meta?: Record<string, unknown>): void
// writes data/cache/{key}.json. The two API routes call this after a real model call.
```

Both API routes do the same thing: compute the key from the exact prompt text, check the cache
first, only call Gemini on a miss, and write the result back. Because the key is a hash of the
*entire prompt* (not just the input text), changing `lib/prompts.ts` invalidates every cache
entry automatically — you can't accidentally read a response shaped for an old prompt.

**Practical upshot for you:** the 4 personas' `rawStory` values in `data/personas.json`, and the
Beat-7 employer vacancy text in `DEMO.md`, all have committed cache entries. Submit those exact
strings through the routes and you get instant, offline, deterministic responses. Anything else
you type will genuinely call Gemini and needs `GEMINI_API_KEY` set locally.

## 4. `lib/` function reference

`lib/types.ts` has **no logic, only types** — it's the contract every other file codes against.
Read it first if a shape below is unclear; it's the source of truth, this doc just narrates it.

### `lib/normalize.ts` — free text → skill ID, deterministically, no LLM

```ts
normalizeText(s: string): string
// lowercase, strip punctuation, collapse whitespace. Used internally; rarely needed by UI code.

normalizeSkillMention(input: string): NormalizationResult
// The main entry point. Cascades: exact alias -> exact canonical name -> containment -> token
// overlap -> null. { input, skillId: string | null, stage, overlapScore? }

normalizeSkillMentionExactAliasOnly(input: string): NormalizationResult
// Ablation variant (scripts/eval.ts only) — exact alias match ONLY. Not for app code.

getSkill(id: string): Skill
// Look up a skill by ID. THROWS if the ID is unknown — a bad ID is a bug to surface, not hide.

allSkills(): Skill[]
// The full taxonomy, for building skill pickers / dropdowns.
```

### `lib/extract.ts` — turns raw model JSON into validated domain objects

This is where the model's output is NOT trusted by default — every claim survives schema
validation, verbatim-span verification, taxonomy normalization, and dedup, or it's dropped.

```ts
class ExtractionError extends Error {}
// Thrown/used to signal "model output was malformed" — caught by the API routes' retry loop.

parseModelJson<T>(raw: string): T
// Strips markdown fences models sometimes add despite instructions not to, then JSON.parse.

ingestCandidateExtraction(
  raw: CandidateExtractionResponse,
  story: string,
  normalize = normalizeSkillMention   // 3rd param exists for the eval ablation; ignore it
): CandidateIngestResult
// THE function for the candidate side. Validates spans against `story` verbatim, normalizes
// each mention to a skill ID, dedups (same skill claimed twice -> keeps the stronger tier).

heldSkillIds(claims: SkillClaim[]): Set<string>
// The skills that actually COUNT for matching. Filters out `implied` claims unless
// userConfirmed is true. THIS is why Beat 4 in DEMO.md matters — an unconfirmed implied claim
// is invisible to feasibility/scoring/the optimizer until the candidate says yes.

buildVerificationQuestions(claims: SkillClaim[]): VerificationQuestion[]
// One question per unconfirmed implied claim, from a lookup table (lib/prompts.ts) — NOT a
// third LLM call. This is Beat 3's data source.

applyVerificationAnswer(
  claims: SkillClaim[],
  skillId: string,
  answeredYes: boolean
): SkillClaim[]
// Answering yes promotes that claim's tier to "demonstrated" and sets userConfirmed: true.
// Returns a NEW array (doesn't mutate) — this is Beat 4's state transition.

ingestJobExtraction(raw: JobExtractionResponse, opts: {
  id: string; employerName: string; location: GeoPoint; areaName: string; rawDescription: string;
}): JobIngestResult
// Employer-side equivalent. Applies a default shift (9am-6pm, Mon-Sat) ONLY if the employer
// said nothing about timing — missingFields tells you which fields were defaulted, so the UI
// can flag them as unstated rather than presenting a guess as fact.
```

### `lib/feasibility.ts` — Stage 1: boolean gate, no scoring

```ts
checkFeasibility(candidate: Candidate, job: Job): FeasibilityResult
// One job. { jobId, feasible: boolean, reasons: InfeasibilityReason[], bestCommute }
// Checks fire independently: salary_below_floor, commute_too_long, schedule_conflict,
// insufficient_hours, no_transport_route, missing_hard_eligibility. ANY reason -> infeasible.

filterFeasibleJobs(candidate: Candidate, jobs: Job[]): FeasibilityResult[]
// Runs checkFeasibility across a job list. One result per job, in the same order.
```

**Never treat feasibility as a score.** A job paying below the candidate's floor is not a weak
match, it's not a match. Don't build a UI that shows infeasible jobs with a low percentage — they
should not appear in the main results at all (near-miss/optimizer views are the exception, by
design — see `lib/optimizer.ts`).

### `lib/scoring.ts` — Stage 2: ranks the survivors only

```ts
DEFAULT_WEIGHTS: ScoreWeights
// { skillCoverage: 0.35, experienceRelevance: 0.15, commuteMargin: 0.2,
//   salaryHeadroom: 0.15, scheduleComfort: 0.15 }. Expose these as UI sliders (CLAUDE.md §3).

scoreJob(
  candidate: Candidate,
  job: Job,
  feasibility: FeasibilityResult,
  weights = DEFAULT_WEIGHTS
): MatchResult
// THROWS if `feasibility.feasible` is false or `feasibility.jobId !== job.id` — this function
// must only ever be called on a job that already passed checkFeasibility. Returns a 0..1 score
// plus 5 ScoreComponents, each with a plain-language `explanation` string ready to render
// directly in a job explanation panel (Beat 5) — you don't need to write your own copy for this.
```

### `lib/optimizer.ts` — the "jobs unlocked per 10 hours" engine, exact not greedy

```ts
missingSkills(job: Job, heldSkillIds: Set<string>): string[]
// requiredSkills(job) minus heldSkillIds. Empty array means the candidate qualifies today.

computeOpportunitySnapshot(feasibleJobs: Job[], heldSkillIds: Set<string>): OpportunitySnapshot
// { feasibleCount, qualifiedCount, qualifiedJobIds, medianSalary }. This is your "N of M jobs
// qualified" headline number (Beat 4's match summary).

pruneSkillUniverse(feasibleJobs: Job[], heldSkillIds: Set<string>): string[]
// Skills that appear in at least one missing(job) — usually 25-45 of the 113. Internal to
// recommendSkillBundles; you probably don't call this directly.

recommendSkillBundles(
  feasibleJobs: Job[],
  heldSkillIds: Set<string>,
  learnHoursBySkillId: Map<string, number>,   // build from skills.json: skill.id -> skill.learnHours
  k: number                                    // max bundle size, use 3
): SkillBundleRecommendation[]
// THE Opportunity Simulator function (Beat 6). Sorted best-first by jobsPer10Hours. Bundles can
// be >1 skill because unlocking a job sometimes needs two skills together with zero gain from
// either alone (e.g. Tally + GST) — this is exact enumeration, not a greedy loop, specifically
// so it doesn't miss that case. Take bundles[0] for the headline metric.

computeNearMissFrontier(feasibleJobs: Job[], heldSkillIds: Set<string>): NearMissJob[]
// Feasible jobs missing exactly ONE required skill — { jobId, missingSkillId } pairs. Good for
// a "so close" list somewhere, though it's not one of the 4 screens below.
```

### `lib/commute.ts` — haversine estimate, no routing API, label it as an estimate in the UI

```ts
estimateCommute(from: GeoPoint, to: GeoPoint, mode: TransportMode): CommuteEstimate
// { mode, straightLineKm, roadKm, minutes }. roadKm = straightLineKm * 1.35, fixed +8min penalty.

bestCommute(from: GeoPoint, to: GeoPoint, availableModes: TransportMode[]): CommuteEstimate | null
// Fastest of the candidate's available modes. null if availableModes is empty.
```

### `lib/prompts.ts` — the only two LLM prompts in the system

You won't call these directly from UI code (the API routes do), but two exports matter for the
verification screen:

```ts
VERIFICATION_QUESTIONS: Record<string, string>
// skillId -> hand-written yes/no question. ~35 common implied skills have one.

genericVerificationQuestion(canonicalName: string): string
// Fallback for any implied skill without a hand-written entry: "Did {name} form a regular
// part of your work?" — buildVerificationQuestions() in extract.ts already applies this
// fallback for you; you shouldn't need to call it directly.
```

## 5. The demo screens (`DEMO.md`), and what each needs

`DEMO.md` walks through 7 narrative beats, but they group into **4 screens** you actually build —
beats 1–4 all live on one continuous candidate-profile page, since submitting a story and then
answering its verification questions is one flow, not separate pages.

### Screen 1 — Candidate Story & Skill Profile (DEMO.md Beats 1–4)

Story textarea → submit → renders claims with evidence highlighted → inline verification
question(s) → live-updating qualified count.

- `POST /api/extract-candidate` — submit the story, get back `CandidateIngestResult`
- `SkillClaim.evidenceSpan` + `spanStart`/`spanEnd` — highlight the matching substring of
  `Candidate.rawStory` for each claim
- `buildVerificationQuestions(claims)` — render one question per unconfirmed implied claim
- `applyVerificationAnswer(claims, skillId, true)` on "yes" — get back updated claims
- `heldSkillIds(claims)` — recompute after every answer; this is what feeds everything downstream
- `filterFeasibleJobs(candidate, jobs)` then `computeOpportunitySnapshot(feasibleJobs, held)` —
  the qualified-count number that visibly changes when she confirms (Beat 4's whole point)

### Screen 2 — Job List & Explanation Panel (DEMO.md Beat 5)

Browse feasible jobs, click one to see why it's a match, in plain set arithmetic — no percentage
score on this panel, that's Stage 1 (feasibility), not Stage 2 (scoring).

- `filterFeasibleJobs(candidate, jobs)` — the list itself; only show `feasible: true` results
- `missingSkills(job, heldSkillIds)` — should be empty for anything in this list; if you also
  show near-miss jobs, this is what tells you which single skill is missing
- `FeasibilityResult.bestCommute` — minutes + mode, label it as an estimate
- For the explanation panel specifically, `scoreJob(candidate, job, feasibilityResult)` gives you
  `MatchResult.components`, each with a ready-to-render `explanation` string

### Screen 3 — Opportunity Simulator (DEMO.md Beat 6)

The headline screen — largest element on it is the top bundle's jobs-per-10-hours number.

- `recommendSkillBundles(feasibleJobs, heldSkillIds, learnHoursBySkillId, 3)` — call once,
  render `bundles[0]` big, `bundles[1..]` smaller as alternatives
- `learnHoursBySkillId` — build from `skills.json`: `new Map(skills.map(s => [s.id, s.learnHours]))`
- `getSkill(skillId).canonicalName` — bundle skill IDs need this to become display labels

### Screen 4 — Employer Vacancy Input & Shortlist (DEMO.md Beat 7)

Plain-language textarea → structured job → run every persona's feasibility+qualification against
it, same functions as Screen 2 just with the candidate/job loop inverted.

- `POST /api/extract-job` — submit the vacancy description, get back `JobIngestResult`
- `JobIngestResult.missingFields` — surface these ("employer didn't say a salary") rather than
  silently using the defaults `ingestJobExtraction` applied
- For each persona: `checkFeasibility(candidate, job)` then, if feasible,
  `computeOpportunitySnapshot([job], heldSkillIds(claims)).qualifiedCount === 1` tells you if
  they're in the shortlist (or just check `missingSkills(job, held).length === 0` directly)
